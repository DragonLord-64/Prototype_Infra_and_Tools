# demo-monitor

A demo showing how Prometheus can be used for monitoring and how Grafana can
dynamically create dashboards to visualize state, using readily available
tooling.

## Concept

Two containers pretend to be servers on a network. Each runs a Prometheus
exporter, and Grafana visualizes what they report.

### Container 1: Server

- Runs the standard Prometheus **node exporter**.
- Also runs a small custom exporter with three fluctuating numeric metrics
  (`server_param_a/b/c`), configurable via a mounted JSON file.

### Container 2: Switch

- Runs a **custom exporter** with configurable thresholds and telemetry.
- Simulates each network interface's:
  - **Link status** — injectable, so a link failure can be simulated on
    demand.
  - **Packet counts** — increments by 1 every half second, just to show
    the interface is alive.

## Telemetry simulation

All telemetry is simulated. Values are generated by a simple Python script
that takes a starting value and adds a small random number to it over time.

## Server (server-container)

The server container is implemented: a single lightweight image (~118MB)
built by copying the static node_exporter binary from the official
prom/node-exporter image onto a python:3-alpine base — no extra runtime
dependencies, keeping it cheap to run many at once. Alongside node_exporter,
a small stdlib-only Python exporter serves three numeric gauges
(`server_param_a/b/c`) that random-walk on a timer to simulate fluctuating
telemetry. Starting values, step size, and update interval live in a
mounted, editable JSON config file, so behavior can change without
rebuilding. Verified via `docker compose up --scale server=10` with no port
conflicts, since nothing is published to the host.

## Switch (switch-container)

The switch container is implemented: a single lightweight image (~83MB, no
pip dependencies) built on `python:3-alpine`, running one stdlib-only
Python process. It simulates 32 network interfaces, each reporting three
Prometheus series -- `switch_interface_rx_bytes_total`,
`switch_interface_tx_bytes_total`, and `switch_interface_link_up` -- for 96
series total. The two counters random-walk upward every half second while
a link is up, and freeze the moment it goes down. Link failures are
injectable on demand via `POST /interfaces/<name>/link?state=down`, so a
demo can show a switch port dying live. Interface count, counter ranges,
and tick interval all live in a mounted, editable JSON config file.
Verified locally: correct series count, counters freeze on link-down and
resume on link-up, idle RSS ~12MB per container -- cheap enough to run
many at once.

## Prometheus (prometheus-agent)

Prometheus runs as its own container, not installed on the host VM. It is
defined in `demo-monitor/docker/docker-compose.yml` alongside the server,
switch, and Grafana containers, all joined on a shared `demo-monitor-net`
Docker network. Scrape config lives in `demo-monitor/prometheus/prometheus.yml`,
mounted read-only into the container. The fleet is 6 named server units
(`VCCU_1:FHS_1`, `VCCU_2:FHS_2`, `FSPU_5:FHS_1..4`) and 3 named switches
(`VCCU_1:SWITCH`, `VCCU_2:SWITCH`, `FSPU_5:SWITCH`), each a distinct
static scrape target carrying a `server_id`/`switch_id` label with its unit
name -- none exposed to the host, reachable only over the compose network.
Prometheus polls itself plus all 15 exporter targets every 15s. The web UI
is at `localhost:9090`. Run `docker compose up -d --build` from
`demo-monitor/docker/` to bring up the whole stack.
